## Conclusion

P2 is not admitted as a local rewrite of awaitWithCheckCanceled or fileCreated. A wider asynchronous business continuation remains possible in principle, but its actual caller has not been identified in this incident. Keep BLOCKED_CONTRACT / REJECTED_LOCAL_REWRITE.

## Three checks

1. Consumers: EditorConfig ConfigEncodingManager.kt:11-17 synchronously reads getCachedEncoding; absent data returns null. EncodingProjectManagerImpl.java:190-198 then continues its other encoding/default lookup. EditorConfigUtf8BomOptionProvider.kt:9-13 calls getUseUtf8Bom; EditorConfigEncodingCache.kt:70-84 synchronously computes on cache miss. PersistentFSImpl.java:978-1003 createChildFile processes the creation event, then checks child charset and isUtf8BomRequired before returning. Thus delaying only the listener can either change encoding selection or move the synchronous computation to the BOM consumer. This is a concrete current-source consumer, not proof that it was the first consumer in the historical incident.
2. Async boundary: row357 input.raw_stack frames37-66 contain transferred-write-action event dispatch, not the original creating business caller. PersistentFSImpl.java:1801-1810 dispatches after-events; createChildFile requires write access and returns VirtualFile synchronously. Neither it nor the provider contracts currently exposes a pending result. Safe P2 needs an outer caller that can suspend the dependent create/write/open continuation without holding the write lock or waiting on EDT. No such incident-specific boundary has been established. Moving a wait into another executor while EDT joins it does not resolve this.
3. Freshness/lifecycle: Utils.kt:276-283 clears EditorConfigPropertiesService cache and increments its modification count. EditorConfigStatusListener.java:84-85 resets the encoding cache. EditorConfigEncodingCache.kt:87-104 computes, publishes cache data and changes file charset, without an asynchronous generation check. reset and setIgnored also have no task generation. A proposed async implementation needs a request generation plus file identity/path and relevant configuration/root/settings versions; reject stale results, respect ignored/manual encoding changes, cancel on project disposal, and serialize validation/publication. Document/content changes must also be checked if continuation writes or reloads contents. Configuration changes require bounded rescheduling, never an EDT wait. Preserve existing no-config/parse-error behavior; propagate cancellation, distinguish failed computation from a valid absent encoding, and never publish success after failure. These are requirements, not implemented protections.

## Evidence limits and next step

### Follow-up: can consumers join the continuation?

Further source verification on 2026-09-28:

- FileEncodingProvider.java returns Charset and Utf8BomOptionProvider.java returns boolean; neither contract represents pending work. Returning null/false while pending is an observable encoding decision, not suspension.
- VirtualFile.java:400-418 requires write lock and synchronously returns the created file. PsiDirectoryImpl.java:395-405 immediately obtains PSI from that file and returns it. Moving only the encoding consumers after this return breaks the existing completion boundary.
- A concrete outer callback exists in CreateFileAction.java:67-80 (elementsConsumer). Its create method at107-111 nevertheless runs directory.createFile inside WriteAction.compute and immediately returns PsiElement[]. An action-specific redesign could prepare configuration asynchronously BEFORE creation and invoke the existing creation/result consumer only after valid preparation. It must make the listener consume prepared data too: computeAndCacheEncoding currently uses withCache=false, so merely warming the encoding cache does not remove its synchronous query. This is a candidate P1-preparation plus P2-continuation design, not a proven pure await-to-callback transformation.
- The saved incident contains exactly one thread, AWT-EventQueue-0. Its transferred-write-action frames do not identify CreateFileAction or any original background sender. The action above is a current-source example, not an identified caller of row357.

Decision: consumers cannot be transparently attached to a later callback under the existing synchronous creation contract. A redesigned outer business operation can potentially defer the entire dependent flow, but row357 cannot be admitted as supported until its actual sender is identified.
