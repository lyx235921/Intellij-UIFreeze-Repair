# S1 修复器构造工作规范

确立日期：2026-09-27。来源：用户确认的工作套路，并要求后续每次启动 S1 修复器构造都遵循。

本文件规定工作方法，不维护活动任务。当前任务、暂停案例及下一证据门以 [PROGRESS](../../PROGRESS.md) 为准；用户本轮指令决定范围。此流程是构造规范，不代表所有环节已经自动化。

## 启动要求

每次开始或恢复 S1 修复器构造，先读取 PROGRESS、本规范以及当前案例报告，核对已有产物和未完成验证。复用已有证据，不重复已完成的实验；不自行恢复用户已暂停的案例。按项目规则完成适用的工作区和研究更新检查。

## 1. 从真实堆栈选例

按用户指定或待处理的卡顿点方法名，在真实堆栈表中寻找案例。记录工作簿、工作表、行号、完整方法符号、UI 线程状态、栈顶和相关调用路径。同一记录内重复栈帧不重复计数。

以真实卡顿记录为问题输入，不额外设置泛化的“是否昂贵”证明门槛；但方法名命中并不证明某种源码变换安全。区分真实栈事实、源码推断和未知信息。

## 2. 用 Finder 定位源码

实际运行 Finder，保留输入、命令和输出，核对定位的文件、类、方法及行号。缺少插件/JDK源码、版本不一致、定位歧义都应明确记录。

必要时使用固定提交的公开源码构造参考候选，保留来源与哈希；未确认事故版本时，不宣称定位到了事故版本或补丁可直接应用。不要把更上层框架源码误当成缺失的目标业务源码。

## 3. 用 Repair 识别候选问题

运行现有分类器：Q1–Q5 是问题一级候选，Q1.x 等是问题二级候选，允许一条记录命中多个二级类别。S1 是修复方法池，P1/P2/P3 是其中的修复方案。

保留实际分类结果和命中证据；当前某个入口尚未接入时如实说明，不把人工分析当作工具输出。Q1 按既有 UI 状态和栈顶规则识别，不在本步骤扩展等待或锁问题。

## 4. 用 extract_method 提取并核验上下文

沿真实调用栈向上最多提取五层非 JDK 方法，取得完整方法正文及来源。沿用现有层数、未定位和栈缺口规则，不伪造缺失调用关系。

核对返回的方法身份、正文范围及源码哈希。寻找能够改动的业务方法，而不是直接修改 JDK/native 栈顶。只补读会影响修复判断的调用者、结果消费者、线程/锁约束、状态与生命周期代码。

不默认要求全调用图或穷尽静态证明；具体影响安全性的信息不足时，记录缺口并限制候选适用范围。

## 5. 先按方法初选，再按源码选择 P1/P2/P3

`repair_selection` 的目标流程是：按卡顿点方法给出 P1/P2 初始顺序，再结合提取的源码和前置条件筛选当前证据支持的方案。

- **P1 提前准备**：输入提前可用，结果能够在关键区域消费；检查新鲜度、版本和原有完成语义。
- **P2 后台执行**：准备工作可离开 EDT，线程依赖允许分离；检查结果提交、生命周期、过期结果及异常处理。
- **P3 延迟操作**：仅在 P1、P2 均明确不适用或失败后尝试，并确认工作可以延迟。

证据不足、源码未找到、生成器未实现都不等于方案失败。方法优先级只是初选，不保证可修或全局最优。多个方案可行时说明选择理由。

## 6. 在 S1 中构造修复器

命名要求（用户确认，2026-09-27）：新建 P1 相关文件以 `P1` 开头，不使用 `Q` 或 `Q1.x` 前缀；问题类别放在内容中说明。文件命名不能替代对实际修复策略的准确记录。

适用条件集中放入 `RelocationPreconditions`；补丁生成逻辑放入 `main/kotlin/src/pool/s1_expensive_work` 的对应修复器。`extract_method.kt` 和 `repair_selection.kt` 同样放在该 S1 目录内，专用于 S1 的方法提取与修复选择（2026-09-28 用户确认）。

从具体案例形成明确的源码变换和拒绝条件。可以先实现受限模板或固定源码版本候选，明确边界；不能只绑定 Excel 行号，也不能仅凭相同方法名对任意调用方套用补丁。

输出修复目标、源码上下文、补丁、适用性、未解决限制和应用状态。默认生成可审阅候选；实际应用按用户授权范围执行。专用入口尚未接入统一选择器时要说明。

## 7. 验证补丁是否有效

依次完成适用的最小验证：

1. 补丁能否应用，生成后的代码是否符合预期。
2. 相关代码能否编译，必要行为测试是否通过。
3. 是否保持同步完成语义、返回值、异常、线程约束、版本及生命周期行为。
4. EDT 响应或相关性能是否改善，明确实验数据、替身和人工延迟。
5. 在匹配版本的目标 IDE 中验证真实场景的行为与卡顿改善。

行为回归时，即使响应变快也判为修复失败。受控实验不能写成真实事故已解决；未完成的验证保留为未验证，不阻止记录已取得的候选成果。命令退出成功也不自动代表修复有效，应检查测试实际证明的结论。

## 8. 记录结果与收尾

更新 [REPAIR-RESULTS](REPAIR-RESULTS.md)：栈中方法、实际修改方法、记录行号、方案、修复程度、生产应用状态、剩余限制及证据链接。同一补丁覆盖多条记录只算一份方案；逐条静态覆盖不等于逐条真实效果验证。

在案例报告保存准确命令、产物路径、测试结果以及观察/解释/不确定性。项目状态有实质变化时更新 PROGRESS 的当前结论、阻塞和下一证据门，保持唯一活动任务入口。不得为了标记完成而把“定位成功”“生成候选”“受控验证”“真实场景验证”混为一谈。
