案例：真实堆栈表第 357 行，EditorConfig / VFS 路径  
目标方法：`ProgressIndicatorUtils.awaitWithCheckCanceled`

## 已确定的实验选择

用户已同意暂定 **100 ms 为总等待实验预算**。这是用于构造和测试候选修复的参数，不是已验证的生产阈值，也不是从真实正常耗时分布推导出的上界。

预算应覆盖本次完整等待，保留取消检查，各轮检查不能重新计时。可以用 50 ms、200 ms 作对照，但它们尚不是选定的部署参数。

这里 P1 指 **Pool S2 / BOUND_WAIT（有界等待）**，不是 S1 的提前准备策略。当前只是确定实验设计，尚未因此生成或应用补丁。

## 为什么设置预算仍不能直接完成修复

真实 EDT 堆栈中的关键路径：

```text
EditorConfigEncodingCache.VfsListener.fileCreated
→ computeAndCacheEncoding
→ EditorConfigPropertiesService.getProperties
→ VirtualDirectoryImpl.findChild
→ LocalFileSystemImpl.fetchCaseSensitivity
→ DiskQueryRelay.accessDiskWithCheckCanceled
→ ProgressIndicatorUtils.awaitWithCheckCanceled
→ FutureTask.get → Unsafe.park
```

上层需要查询结果来确定文件查找和编码行为。等待超过 100 ms 后，必须决定如何结束或继续业务；单纯抛出异常不能证明整个操作正确退出。

当前源码显示，创建流程会先处理创建事件，然后检查编码/BOM 并返回文件。因而超时发生时可能已经存在副作用；退出等待不等于文件创建被回滚。还需核验异常是否被事件分发层捕获，以及创建方是否仍然继续执行。

| 决策 | 可讨论的选择 | 当前建议 |
| --- | --- | --- |
| 超时后业务如何结束？ | 明确失败、取消操作、稍后重试，或其他经验证的降级 | 先研究明确失败并停止依赖该结果的后续操作；不猜测编码或大小写敏感性。是否能够安全停止尚未证实 |

需要特别讨论：**为了避免长时间冻结，是否接受本次操作失败？失败时允许留下已经创建但尚未完成后续处理的文件吗？应提示用户、清理还是保留？** 清理和回滚不能在未核验数据归属、事件和用户编辑的情况下自动实施。

## 不应采用的默认处理

- 超时就返回任意默认编码或大小写敏感性：可能改变业务结果。
- 捕获超时后立即无限重试：重新引入无界等待。
- 将每一轮等待设置为 100 ms，但没有总预算：仍可能无限等待。
- 无条件取消共享查询 Future：可能影响其他调用者。
- 抛出超时异常后就宣称修复完成：异常可能被吞掉，已有副作用也未必回滚。
